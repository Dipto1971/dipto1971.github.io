 To solidify my understanding, I began working on more advanced projects. One of these was a Google Meet clone. I built this specifically to test and deepen my practical knowledge of WebRTC. Building this project required me to master the four core pillars of WebRTC architecture. First, I implemented a signaling server using WebSockets. This was used to exchange initial connection data between peers. Second, I integrated STUN servers. These allow devices to discover their own public IP addresses and bypass basic firewalls. Third, I learned to configure TURN servers. These act as reliable relays for media streams whenever direct peer connections fail due to strict network configurations. Finally, I managed the exchange of ICE candidates. This is a crucial process. It involves gathering all possible network routing paths and dynamically negotiating the most efficient route for real-time video and audio transfer between clients.

 Following that, I turned my attention to the backend. I wanted to study how the single-threaded nature of Node.js operates in practice. This ultimately led me to take a thorough deep dive into Node.js architecture. I spent considerable time understanding the Event Loop and how it manages concurrent operations. The main JavaScript execution runs on a single thread using the V8 engine. However, Node.js handles concurrent requests efficiently by offloading asynchronous tasks. These include database queries or file system operations that are sent to the libuv library. Once these background tasks finish, libuv pushes the callbacks back into the event queue. The Event Loop then processes them sequentially. This non-blocking input and output model is highly effective. It is exactly what allows Node.js to handle thousands of concurrent connections seamlessly. It achieves this without the memory overhead of creating a new thread for every individual request.
